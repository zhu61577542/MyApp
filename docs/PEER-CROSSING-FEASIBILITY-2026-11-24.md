# 两台电脑双向对等跨屏可行性验证

基线：0.1.9-alpha / 5e81d662。用户授权本轮先清理本机，再验证双向改造的代码范围和风险。本轮新增后台验证及文档，没有实现或打包双向功能，没有操控实际键鼠或执行GUI自动化。

## 结论

两节点双向跨屏可行，可以复用现有双工TLS/Link和捕获、注入、拓扑、恢复组件。连接由谁发起和键鼠由谁提供需要分开处理；界面可取消固定主副，而底层保留内部的连接发起/监听分工。直接删除角色检查或同时开启现有捕获器会产生控制冲突和输入回环，不能作为实现方案。

新增 internal/app/bidirectional_feasibility_test.go 使用真实app.Link、两组net.Pipe及内存注入器，在同一连接中依次验证A→B、B→A的控制确认、鼠标坐标、键盘按下/释放和结束释放。race检查通过。它证明通道基础可以复用，不是实体双向跨屏验收，也没有证明双方同时申请时已经互斥。

## 已核查的改造范围

| 范围 | 当前事实 | 下一阶段要求 |
|---|---|---|
| 运行时 | cmd/myapp/controller.go 的runControllerOnce创建无injector的Link；service.go的runConnected只为监听端装gate，不装capture/runEdges | 两端按协商同时具备按需捕获和注入能力 |
| 角色约束 | transport.ExchangeHello拒绝相同角色；config.Validate禁止agent配置peers；device.Manager.Activate、app.ControlMachine.BeginEnter限制agent发起 | 保留旧连接约束作兼容，分离动态输入角色；不要广泛删除安全检查 |
| 控制权 | app/desktop.go请求只含ID/action/entry；本机Generation不随网络输入传递 | 将控制源绑定认证设备，增加控制代次/租约、撤销及过期输入拒绝 |
| 防回环 | Mac Capturer.handleEvent未检查注入来源；Windows LLHook已有injected过滤，但Position轮询无法区分远端移动 | 标记并过滤自身注入；被控态禁止因远端移动再次触边发起 |
| 本地接管 | 非捕获态只有指针位置轮询 | 增加不拦截的实体输入观察，本地接管先撤销旧代次并释放按键 |
| 多屏源端 | runEdges/Watcher只看主屏矩形；Windows已有完整Topology；Mac尚未枚举多屏 | Windows按真实外侧边缘触发，内部接缝不切换；Mac多屏另补枚举或明确首版单屏范围 |
| 权限与界面 | Mac输入监控检查/请求以controller角色为条件；Snapshot.Target的含义依赖固定角色 | 改按输入能力申请；界面显示当前控制来源和目标，不让用户选择固定主副 |
| 配对数据 | trust.Record没有固定角色，证书身份独立 | 迁移时保留身份和信任；连接地址、互反位置及旧版混用另做明确兼容测试 |

旧临时PowerShell输出的peerCount=1不能证明有效agent配置含一个peer：实际Validate禁止该配置，@($null)也可能计为1。此计数不作为架构判断依据。

## 建议实施顺序

1. **控制权状态机**：先完成本地、申请、发送、接收、恢复状态；定义同时触边裁决、本地优先接管、紧急退出、断线和租约失效。先用后台测试证明任意时刻只有一个有效控制源，迟到确认/输入无效，释放幂等。
2. **能力协商及双向装配**：首版只做Mac与Windows两节点，复用一组现有会话；协商新能力和控制代次，双方都装捕获/注入组件。现有严格JSON不允许随意加字段，必须采用新可选消息或明确协议升级。旧端混用须安全降级或提示升级。
3. **平台输入及几何**：补Mac注入来源过滤、两端被控态抑制与实体输入接管；再把Windows多屏源端对外边缘接入。实际本地操作收回控制时优先恢复本机，不等待远端网络确认。
4. **迁移与界面**：保留现有证书/信任和用户位置，生成互反布局；取消固定主副选择，只显示本机、正在控制和正在接受控制等动态状态。
5. **实机验收**：后台通过后再请用户使用双方各自的实体键鼠，验证双向触边、Windows双屏、同时操作、断网、休眠恢复、权限撤销及显示器变化。之后再考虑多机自动协调。

多机自动选举、任意节点输入转发和协调者离线恢复不纳入首轮两节点实现，避免同时改动已验证的文字与文件中继。
