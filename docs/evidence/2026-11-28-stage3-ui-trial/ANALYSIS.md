# 第三阶段首轮UI日志分析

版本0.1.13-alpha-stage3，源码dbaa0cbb。用户于2026-11-28启动双端GUI并人工测试，当前未通过验收；未修改程序或操作用户键鼠。

## 事实与用户反馈

本轮从Mac首次新版启动09:47:02起分析，排除之前旧进程反复连接失败的日志。两个实际程序进程路径均为0.1.13包。两端GUI与desktop-service为正常父子进程，不据两个PID判定重复GUI。

截至本次采集，Mac与Windows日志各记录15次Mac→Windows的Active，没有Windows→Mac的Active记录。Active只证明控制状态建立，不据此认定每个键鼠动作均正常。Windows至少记录一次“本机实体操作已接管”。

用户确认使用Windows实体鼠标从整组桌面最右边缘尝试进入Mac，初次未成功；先从屏幕中央移动后反馈鼠标可进入，但成功不稳定；使用Windows实体键鼠时，中英文和数字均无法输入。此反馈与缺少反向控制生效日志需要进一步核对，不能单凭鼠标显示位置确认反向控制稳定建立。

Mac09:47:03曾提示输入监控未授权，后续重新启动后出现双方就绪和实际控制状态，故不能把后续所有失败都归为未授权。期间记录了多次心跳/EOF重连，用户确认主动退出并重启过程序；具体操作与断线尚未逐次对应，不单独归因为网络故障。两端时钟还存在偏差变化，不用跨端日志时间差推算切换延迟。

## 已复现的代码缺陷

`pointer.Landing`将Mac进入Windows的落点放在右边缘内侧约2像素；`Watcher.Observe`在初始化或恢复后要求先进入距边缘至少约6像素的内部区域才重新待命。因此远程鼠标刚进入Windows后，拿起Windows鼠标直接继续向右，即使到达最右边缘，也不会触发。真实函数的Docker复现见edge-reentry-reproduction.log：直接向右持续不触发，先向内再向右可触发。

此前回归从屏幕内部起步，没有覆盖远程落点边缘立即换用本机鼠标的自然接续场景。该缺陷与初次失败现象一致，但不能据此解释全部反向不稳定与键盘问题。

`desktop_edges.go`在同一轮Local采样中先写“双向边缘监视已就绪”，随后写“边缘监视已就绪”，造成状态与日志反复交替。应统一状态更新，避免无意义刷新；尚无证据证明它就是心跳断线的根因。

## 当前证据不足

现有控制日志按快照采样，缺少每次触边申请、完整token/恢复原因及键盘捕获、发送、接收、注入的汇总计数。不能确定键盘停在捕获、控制权、传输、注入还是目标焦点环节，也不能仅凭本轮日志判断为输入法问题。大部分`[error]`条目是正常控制状态被写入stderr，不应按error标签总数计算故障。

后续应修复自然接续的边缘重新待命逻辑并保持注入/恢复位置不会自动反弹；统一就绪状态；补充只记录数量与原因、不记录具体按键或坐标轨迹的诊断，再逐项人工验证双向、键盘及实体接管。第四阶段未开始。
